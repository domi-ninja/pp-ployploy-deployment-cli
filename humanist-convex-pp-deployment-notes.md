# Humanist Convex/Vite pp Deployment Notes

Status: deployed to `p3.domi.ninja` with `pp` using a lightweight Docker bundle.

## Working Architecture

- `humanist.design` and `www.humanist.design`: Vite frontend served by an nginx container. `www` redirects to apex.
- `api.humanist.design`: self-hosted Convex backend on container ports `3210` and `3211`.
- `dash.humanist.design`: Convex dashboard on container port `3211`.
- `postgres`: persistent Postgres under `/data/pp/humanist-design/postgres`.
- `s3`: MinIO under `/data/pp/humanist-design/s3` for Convex storage buckets.

The deploy is driven from `../humanist.design/deploy.yml` and uses the extended local `pp` binary.

## pp Extensions Needed

The deployment required extending `pp` beyond the original single-image path:

- multiple services in one compose project
- locally built images plus pulled upstream images
- build args sourced from env
- bind mounts for persistent data
- Caddy route file templates
- service phases: infra/backend first, frontend after hooks
- local deploy hooks after backend health
- smoke checks after route reload

Important sequencing fix: in phased deploys, `pp` now applies Caddy routes immediately after infra/backend services are healthy and before local Convex hooks. The Convex CLI reaches the self-hosted backend via `https://api.humanist.design`, so routes must exist before env push and function sync.

## Convex Admin Key

Do not invent `CONVEX_SELF_HOSTED_ADMIN_KEY`.

The real key is generated by the running Convex backend container:

```sh
/convex/generate_admin_key.sh
```

`../humanist.design/scripts/refresh-convex-admin-key.sh` finds the backend by `pp.project=humanist-design` and `pp.service=convex-backend`, runs the container script over SSH, and writes the key into ignored `.env.local`.

## Root Causes Fixed

- `POSTGRES_URL` must be cluster-level for the Convex image. It must not include the database path.
- Convex uses `INSTANCE_NAME` as the Postgres database name when using `POSTGRES_URL`, so `POSTGRES_DB` is `api.humanist.design`.
- Local Docker Postgres has SSL disabled; Convex backend needs `DO_NOT_REQUIRE_SSL=1`.
- Dashboard image does not have `wget`; its health check uses Node `fetch`.
- MinIO needs buckets created before Convex sync. `scripts/ensure-minio-buckets.sh` uses `minio/mc` with `/bin/sh` entrypoint.
- Convex self-host CLI commands must not use `--prod`; self-host mode is selected by `CONVEX_SELF_HOSTED_URL` and `CONVEX_SELF_HOSTED_ADMIN_KEY`.
- MinIO without KMS rejects Convex's default S3 server-side encryption request. Backend env sets `AWS_S3_DISABLE_SSE=true`.
- `.env.local` is dotenv-style, not shell-safe. Hook scripts must parse needed keys directly instead of `source`ing the whole file.
- The env push script no longer prints the full Convex env list, because that exposes secrets.

## Current Deploy Command

From `../humanist.design`:

```sh
GIT_CONFIG_COUNT=1 \
GIT_CONFIG_KEY_0=safe.directory \
GIT_CONFIG_VALUE_0=/mnt/HC_Volume_105789459/repos/humanist.design \
/tmp/pp-humanist-test deploy
```

The working deployment flow is:

1. Build the Vite/nginx image locally.
2. Upload compose bundle, route file, env files, and image tar to p3.
3. Pull Convex, dashboard, Postgres, and MinIO images on p3.
4. Start `postgres`, `s3`, `convex-backend`, and `convex-dashboard`.
5. Wait for backend/dashboard/Postgres health.
6. Apply Caddy routes.
7. Ensure MinIO buckets.
8. Generate the real Convex admin key from the backend container.
9. Push `.env.local` into Convex.
10. Run `npx convex dev --once --env-file .env.local`.
11. Start the frontend.
12. Reload Caddy routes.
13. Smoke-check frontend and Convex version endpoint.
